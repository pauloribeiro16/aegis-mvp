# Step 5 — Functional Evolution Register (V0 → V1)

> **Finding: evaluated — zero D1/D2/D4 changes, one D3.** The refinement pass returned **no derived requirement, no description refinement, no card split, and one priority re-evaluation**: `R3.3` Operate coordinated vulnerability disclosure, **SHOULD → MUST**, driven by `CRA Annex I Part II (5)` → `SO-D-02.3-001` together with `NIS 2 Art. 21(2)(e)` → `SO-D-02.3-002`. The V0 repertoire already spans the customer/AI product core and the banking-grade operating functions the five regimes demand, so the synthesis proceeded by constraint absorption (`RN11`–`RN26` on 16 of the 43 cards) and chain binding (92 rows on 36 of the 43 cards); the single point at which a confirmed regulation contradicts the V0 priority is `R3.3`.

## 1. Evaluation method

For every accepted constraint (`RN11`–`RN26`) and every one of the 92 chain bindings, the pass asks one question:

> *Does binding this obligation require user-visible, Cockburn Sea-Level functionality that no V0 card covers (D1), a description that cannot host the constraint as written (D2), a priority a confirmed regulation contradicts (D3), or a card bundling functionalities with distinct security surfaces (D4)?*

- **Yes** → a register entry in §3.
- **No** → `evaluated, no change` in the area pass (§2), with the candidate named and the reason for closure.
- The pass is exhaustive over the 11 V0 functional areas and over the four change types; no area and no type is left silent.
